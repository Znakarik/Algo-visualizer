# Инструкция для агента: собрать фильтры из кода в алгоритмы конструктора

## Задача

В исходном коде проекта (дальше «целевой код») есть логика, которая выбирает карты:
отсекает истёкшие, заблокированные, кредитные (если они не разрешены), карты с недостаточным
балансом и т. п. Входом служат флаги или параметры запроса и список карт, выходом отфильтрованный
список или одна карта.

Нужно найти **всю** такую логику и перенести каждую в файл алгоритма `algorithms/<имя>.algo.json`
этого репозитория. Файл должен:

1. открываться в конструкторе (`index.html` → «Открыть файл»);
2. повторять решения целевого кода: те же условия, в том же порядке, с теми же «все/первая»;
3. проходить проверку `node tools/validate.js` без ошибок.

Движок конструктора (`engine.js`) уже умеет выполнять такие алгоритмы. Твоя работа — описать
логику в его формате, а не писать новый код.

## Подготовка

```bash
git clone https://github.com/Znakarik/Algo-visualizer.git
cd Algo-visualizer
node --version        # нужен Node.js 18+
npm test              # всё должно быть зелёным до начала работы
```

Прочитай `README.md`, этот файл и примеры в `algorithms/`:
`podbor-kart.algo.json` (цепочка фильтров), `karty-s-vetvleniem.algo.json` (ветвление) и
`rannie-vozvraty.algo.json` (несколько ранних `return`).

**Не меняй** `engine.js`, `app.js`, `index.html`, `styles.css`, `examples.js` и существующие тесты.
Если чего-то не хватает в движке, опиши это в `algorithms/INDEX.md` в разделе «Чего не хватает в
конструкторе». Решать будет владелец репозитория.

## Формат файла

```jsonc
{
  "format": "algo-visualizer",
  "version": 2,
  "name": "Подбор карт для оплаты",               // по-русски, понятно человеку
  "description": "Что делает алгоритм, одним-двумя предложениями.",
  "source": "payments/src/main/java/.../CardSelector.java#selectCards",  // откуда взят
  "scenarios": [ /* см. «Сценарии» ниже */ ],
  "blocks": [ /* первый блок всегда input */ ]
}
```

`description`, `source` и `scenarios` необязательны для движка, но обязательны для тебя.
Конструктор сохраняет их при пересохранении файла.

### Блоки

У каждого блока есть `id` (уникальный в файле: латиница, цифры, `-`, `_`; например `f-expired`),
`type` и `label`, то есть короткое название по-русски, которое человек увидит в схеме.
Добавляй `source` (файл:строка в целевом коде) к каждому блоку, кроме `input`.

| `type` | Когда использовать | Поля |
|---|---|---|
| `input` | ровно один, первым | `params`, `data` |
| `filter` | оставить карты по условию | `cond` или `condMode:"code"`+`expr`; `take` |
| `branch` | для разных карт разная дальнейшая логика | как у filter + `yes: [блоки]`, `no: [блоки]` |
| `assert` | код бросает исключение / проверяет инвариант | как у filter (без `take`) + `stopOnFail` |
| `sort` | порядок важен (перед «первой совпавшей», или результат отсортирован) | `expr` (обычно `"x.balance"`), `order: "asc" \| "desc"` |
| `map` | вычисляемое поле, нужное следующим условиям | `expr`, например `"({ ...x, available: x.limit - x.used })"` |
| `reduce` | код сворачивает список в одно число | `expr` (`acc + x.balance`), `init` |
| `return` | ранний `return` в коде | `cond` (можно без правил), `trigger`, `value`; см. «Ранние возвраты» |

**`take`** у `filter` и `branch`:
- `"all"` (по умолчанию) — все совпавшие;
- `"first"` — только первая совпавшая по текущему порядку. У `branch` первая совпавшая идёт в «да»,
  все остальные (включая другие совпавшие) — в «нет».

**Ветвление**: после веток списки сливаются: сначала результат «да», затем «нет».
Если в целевом коде одна из сторон карты просто выбрасывает, это не ветвление, а обычный `filter`.
`branch` нужен, только когда **обе** стороны продолжают обработку по-разному.

### Ранние возвраты: блок `return`

Блок `return` — это `return` посреди метода. Если он сработал, **весь** алгоритм сразу
заканчивается с указанным результатом, даже если блок стоит внутри ветки `branch`.
Следующие блоки не выполняются, и конструктор показывает их серыми.

```json
{ "id": "r-debit", "type": "return", "label": "Есть дебетовые с балансом: вернуть их",
  "source": "CardSelector.java:48",
  "trigger": "ifMatched", "value": "matched",
  "cond": { "join": "and", "rules": [
    { "left": { "kind": "field", "name": "type" }, "op": "eq", "right": { "kind": "const", "value": "debit" } },
    { "left": { "kind": "field", "name": "balance" }, "op": "gte", "right": { "kind": "param", "name": "minAmount" } } ] } }
```

- **Совпавшие** — элементы текущего списка, для которых верно `cond`. Без правил совпадают все.
- `trigger` — когда срабатывает: `always` (всегда), `ifMatched` (есть хотя бы одна совпавшая),
  `ifNone` (совпавших нет).
- `value` — что вернуть: `matched` (совпавшие), `first` (первую совпавшую), `all` (весь
  текущий список, без учёта условия), `empty` (пустой список).

| В целевом коде | Блок `return` |
|---|---|
| `if (cards.isEmpty()) return List.of();` | без правил, `trigger:"ifNone"`, `value:"empty"` |
| `if (!creditAllowed) return List.of();` | правило `param creditAllowed isFalse`, `ifMatched`, `empty` |
| `if (flag) return cards;` | правило `param flag isTrue`, `ifMatched`, `all` |
| `var d = cards.stream().filter(P).toList(); if (!d.isEmpty()) return d;` | правила P, `ifMatched`, `matched` |
| `cards.stream().filter(P).findFirst().ifPresent(c -> { return c; })`, цикл `for (c : cards) if (P) return c;` | правила P, `ifMatched`, `first` |
| `Optional<Card> c = ...findFirst(); if (c.isEmpty()) return null;` | правила P, `ifNone`, `empty` |
| `return cards;` в конце метода | не нужен: результат алгоритма и так последний список |
| `return` внутри `if/else` по карте | `branch`, а в нужной ветке блок `return` |

Учти, что правило только на параметре (`param … isTrue`) «совпадает» со всеми элементами. Поэтому
на пустом списке `ifMatched` не сработает, ведь совпавших нет. Если в целевом коде важно, чтобы
возврат по флагу сработал и на пустом списке, поставь перед ним возврат с `ifNone`/`empty`
или отметь это в `INDEX.md`.

Если метод возвращает одну карту (`Card`, `Optional<Card>`), а не список, алгоритм всё равно
возвращает список: из одной карты или пустой. Укажи это в `description`.

`throw` — это не `return`. Для исключений используй `assert` со `stopOnFail:true`.

### Входные данные: `params` и `data`

```json
{
  "id": "in", "type": "input", "label": "Карты клиента",
  "params": [
    { "name": "creditAllowed", "type": "boolean", "value": false },
    { "name": "minAmount",     "type": "number",  "value": 5000 },
    { "name": "currency",      "type": "string",  "value": "RUB" },
    { "name": "operationDate", "type": "date",    "value": "2026-10-22" }
  ],
  "data": "[{\"id\":\"4276 •• 1111\",\"name\":\"Зарплатная\",\"type\":\"debit\",\"balance\":15000,\"expires\":\"2027-03\",\"blocked\":false}]"
}
```

- **params**: всё, что приходит в логику снаружи, кроме самих карт. Это аргументы метода, поля
  запроса, флаги конфигурации, feature-флаги. Имя бери **как в коде** (`creditAllowed`,
  `isCreditAllowed` → `creditAllowed`), латиницей. Типы: `boolean`, `number`, `string`, `date`.
  В `value` укажи значение по умолчанию из кода или самое типичное.
- **data**: JSON-массив тестовых карт **строкой**, тот же JSON, просто экранированный.
  Поля называй как геттеры/свойства в коде без `get`/`is`: `getBalance()` → `balance`,
  `isBlocked()` → `blocked`, `getOwner().getAge()` → `owner: { age: … }`.
  - Даты: `"2027-03"` (действует до конца месяца, как на карте), `"03/27"`, `"2027-03-31"`.
  - Деньги: числа (`15000.50`), не строки.
  - Enum-значения: строкой, ровно так, как ты пишешь их в правилах (`"credit"` или `"CREDIT"`, но
    одинаково везде).
  - У каждой карты уникальный `id` и понятное `name`: по ним сценарии сравнивают результат, а
    человек читает таблицу.

**Тестовые карты подбирай так, чтобы каждое правило хотя бы раз было верным и хотя бы раз
ложным** (проверка это контролирует). Добавь граничные случаи: баланс ровно равен минимуму,
срок истекает в текущем месяце, `null` в необязательном поле.

### Условия: `cond`

```json
"cond": {
  "join": "or",
  "rules": [
    { "left": { "kind": "param", "name": "creditAllowed" }, "op": "isTrue",
      "right": { "kind": "const", "value": "" } },
    { "left": { "kind": "field", "name": "type" }, "op": "ne",
      "right": { "kind": "const", "value": "credit" } }
  ]
}
```

- `join`: `"and"` — все правила, `"or"` — хотя бы одно.
- `left.kind`: `field` (поле карты, через точку для вложенных) или `param`.
- `right.kind`: `const` (значение **строкой**: `"5000"`, `"true"`, `"credit"`), `param`, `field`
  (сравнить с другим полем той же карты), `today` (сегодняшняя дата).
- `op`:

| op | смысл | правая часть |
|---|---|---|
| `eq`, `ne` | равно / не равно (строки с учётом регистра) | да |
| `gt`, `gte`, `lt`, `lte` | `>`, `≥`, `<`, `≤`; числа как числа, даты как даты | да |
| `contains` | строка содержит (без учёта регистра) / массив содержит | да |
| `isTrue`, `isFalse` | `true` / `false` (отсутствующее поле считается `false`) | нет |
| `isEmpty`, `notEmpty` | `null`/пусто / задано | нет |

Для операций без правой части пиши `"right": { "kind": "const", "value": "" }`.

**Если условие не выражается правилами** (вызов метода, арифметика, сложная вложенность),
сначала попробуй блок `map`, который вычислит поле, а затем обычное правило. Если не выходит и
так, используй `"condMode": "code", "expr": "<JS-выражение>"`. В выражении `x` — карта,
`p` — параметры, `i` — номер, `data` — весь список. Каждый такой случай перечисли в `INDEX.md`.

## Как переводить код в блоки

Порядок блоков = порядок операций в коде. Последовательные фильтры работают как «И».

| В целевом коде (Java/Kotlin/JS) | В алгоритме |
|---|---|
| `.filter(c -> cond)`, `removeIf(c -> !cond)`, `if (cond) result.add(c)` в цикле | `filter` с `cond` |
| `.filter(...).findFirst()`, `findAny()`, `.limit(1)`, цикл с `break` (дальше обработка продолжается) | `filter` с `take:"first"` |
| `return` посреди метода, `findFirst()` с немедленным `return` | блок `return`, см. «Ранние возвраты» |
| `findFirst()` без фильтра | `filter` без правил (`rules: []`) с `take:"first"` |
| `if (!creditAllowed) cards.removeIf(c -> c.isCredit())` — условие на флаг, которое включает/выключает фильтр | **один** `filter`, `join:"or"`: `param creditAllowed isTrue` ИЛИ `type ne credit` |
| `if (hasMin) filter(balance >= min)` | `filter`, `join:"or"`: `param hasMin isFalse` ИЛИ `balance gte param minAmount` |
| `if/else` по карте, и обе ветки продолжают обработку по-разному | `branch` с `yes`/`no` |
| `if/else` по флагу, и в ветках разная цепочка фильтров | `branch` с правилом только на `param` (все карты уйдут в одну сторону) |
| `switch (card.getType())` на 3+ варианта | вложенные `branch`: `type eq A` → да / нет → `branch` `type eq B` … |
| `A && (B \|\| C)` | два фильтра подряд: `[A]`, затем `join:"or"` `[B, C]` |
| `!(a > b)` | обратная операция: `lte` |
| `date.isAfter(now)` / `!date.isBefore(now)` | `gt today` / `gte today` (внимательно к «строго») |
| `x.compareTo(min) >= 0` (BigDecimal) | `gte` |
| `x != null`, `StringUtils.isNotBlank(x)` | `notEmpty` |
| `a.equalsIgnoreCase(b)` | `contains` не подходит: нормализуй регистр в тестовых данных и используй `eq`, отметь в INDEX |
| `.sorted(comparing(Card::getBalance).reversed())` | `sort`, `expr:"x.balance"`, `order:"desc"` |
| `thenComparing(...)` (составная сортировка) | `sort` с `expr`, дающим строковый ключ, или отметь в INDEX |
| `if (list.isEmpty()) throw ...`, `require(...)`, `checkArgument(...)` по картам | `assert`, `stopOnFail:true` |
| `anyMatch`/`allMatch`/`noneMatch`, возвращающие boolean | `assert` (если это проверка) или отметь в INDEX: результат не список |
| `map(c -> c.withX(...))`, вычисляемые поля | `map` с `expr` |

Сомнительные места (неочевидный порядок, побочные эффекты, логика в БД/SQL, в аннотациях или
конфиге) **не угадывай**: запиши в `INDEX.md` в «Вопросы владельцу» с указанием файла и строки.

## Сценарии

`scenarios` — запуски с другими значениями параметров и ожидаемым результатом:

```json
"scenarios": [
  { "name": "по умолчанию", "params": {}, "expect": ["4276 •• 1111", "2200 •• 6666"] },
  { "name": "кредитные разрешены", "params": { "creditAllowed": true }, "expect": ["5536 •• 2222", "4276 •• 1111", "2200 •• 6666"] }
]
```

- `expect` — значения поля `expectBy` (по умолчанию `id`) у результата, **в порядке выдачи**.
- `today` в сценарии подменяет «сегодня» (для условий со сроком действия).
- `data` в сценарии (необязательно) заменяет тестовые карты, например `"data": []` для проверки
  `if (cards.isEmpty()) return …`.
- Каждый блок `return` должен хотя бы в одном сценарии сработать, и каждый блок должен хотя бы
  в одном сценарии выполниться. Проверка предупреждает, если это не так.
- Сделай минимум по одному сценарию на каждое значение каждого флага и на каждый порог.
- **`expect` выводи из целевого кода, рассуждая по нему, а не копируй из вывода проверки.**
  Иначе сценарий ничего не проверяет. Если вывод проверки расходится с тем, что ты ожидал по коду,
  ошибка либо в алгоритме, либо в понимании кода. Разберись, не подгоняй.
- Если в целевом коде есть юнит-тесты на эту логику, возьми их входы и ожидаемые выходы в сценарии.

## Проверка

```bash
node tools/validate.js --today 2026-10-22 algorithms/<файл>.algo.json            # кратко
node tools/validate.js --today 2026-10-22 --trace algorithms/<файл>.algo.json    # все шаги
node tools/validate.js --json algorithms/*.algo.json                              # для разбора программой
```

- **Ошибки** (код выхода 1) должны исчезнуть: сломанный JSON, нет `input` первым, ссылка на
  несуществующий параметр, неизвестная операция, падение при выполнении, сценарий не совпал.
- **Предупреждения** разбери. Правило, которое ни разу не было ложным или верным, значит, что
  нужны тестовые данные или сценарий. То же для блока, который ни разу не выполнился, и для
  возврата, который ни разу не сработал. Поле, которого нет в данных, — обычно опечатка. Нет
  `label`/`source` — добавь. Оставшиеся предупреждения объясни в `INDEX.md`.
- В конце `npm test` должен быть зелёным.

Можно собирать файлы скриптом, переиспользуя движок, а не писать JSON руками:

```js
// tools/build-<что-то>.js — временный скрипт, коммитить не обязательно
const E = require('../engine.js');
const fs = require('fs');
const R = E.rule; // R(leftKind, leftName, op, rightKind, rightValue)
const blocks = [
  E.createBlock('input', { id: 'in', label: 'Карты клиента',
    params: [{ name: 'creditAllowed', type: 'boolean', value: false }],
    data: JSON.stringify([/* карты */], null, 1) }),
  E.createBlock('filter', { id: 'f-credit', label: 'Кредитные разрешены?', source: 'CardSelector.java:57',
    cond: { join: 'or', rules: [R('param', 'creditAllowed', 'isTrue'), R('field', 'type', 'ne', 'const', 'credit')] } }),
];
const file = E.serialize('Подбор карт', blocks, {
  description: '…', source: 'payments/.../CardSelector.java#selectCards',
  scenarios: [{ name: 'кредитные разрешены', params: { creditAllowed: true }, expect: ['…'] }],
});
fs.writeFileSync('algorithms/podbor-kart-dlya-oplaty.algo.json', JSON.stringify(file, null, 2) + '\n');
```

`E.run(blocks, { today: '2026-10-22' })` выполняет алгоритм и возвращает `{ output, steps, error }`.
Это удобно для быстрых проверок прямо в скрипте.

## Порядок работы

1. **Инвентаризация.** Найди в целевом коде все места выбора карт. Ищи по словам `filter`,
   `removeIf`, `findFirst`, `stream()`, `Card`, `credit`, `debit`, `balance`, `expir`, `blocked`,
   `minAmount`, `allowed`, `sorted`, `Comparator`, `return`, `Optional`, а также по вызовам этих методов.
   Определи **точки входа**: публичные методы, которые получают параметры и список карт и
   возвращают отфильтрованный список или карту. Один файл = одна точка входа. Если внутри она
   вызывает другие методы с фильтрами, разверни их в тот же файл в порядке вызова и укажи `source`
   у каждого блока.
2. Сначала создай `algorithms/INDEX.md` со списком найденных точек входа. Потом заполняй файлы.
3. Для каждой точки входа: параметры → тестовые карты → блоки → сценарии → `validate` → исправления.
4. Имя файла: латиницей, транслитом названия, `kebab-case`, расширение `.algo.json`
   (`podbor-kart-dlya-oplaty.algo.json`).
5. **Коммиты**: один алгоритм — один коммит, сообщение
   `Алгоритм: <name> (<source>)`. `INDEX.md` — отдельным коммитом в конце.
   Работай в ветке `filters/<название-целевого-проекта>`, не в `main`.
